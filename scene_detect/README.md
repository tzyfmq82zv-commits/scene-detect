# 骨架动作识别（奔跑 / 摔倒 / 打架）

对应实施路线的**里程碑 2**：骨架序列提取 + 三类动作模型训练。

## 四个脚本的关系

```
视频文件
   │  feature_extract.py   （YOLO11-Pose + BoT-SORT，只需跑一次）
   ▼
骨架片段 .npz  +  manifest.csv
   │  人工补标签 → labels.csv
   ▼
   │  dataset.py           （归一化 + 增强，训练时按需读取）
   ▼
   │  model.py             （ST-GCN 或轻量 TCN 基线）
   ▼
   │  train.py             （训练 + 阈值寻优 + 评估）
   ▼
best.pt  （权重 + 每类最优阈值）
```

**奔跑不走模型，走速度规则。** 数据里奔跑只有 8 个正样本（Weizmann 的
10 个视频，每个只能切出 1 段，还有 2 段因为人贴在画面边缘没检出轨迹），
这个量级训不出任何东西。所以：

```
摔倒、打架  ->  ST-GCN 模型（running_rule.py 之外的三个脚本）
奔跑        ->  running_rule.py 的速度规则
正常        ->  两者都不触发
```

跑标定：

```
python running_rule.py --calibrate --save "D:\SceneDetection\features\running_rule.json"
```

实测结果（阈值 1.05 人体身高/秒）：奔跑召回 8/8，**摔倒片段零误报**。
10 个误报里 9 个来自 Weizmann 的 skip/jack/side——这些本身就是高速动作，
属于标注口径问题；另有 1 个来自公交车上快速走动的人。

一个要如实说明的局限：奔跑最低速度 1.08、走路最高 1.72，两者**有重叠**，
所以快步走路的人有可能被判成奔跑。另外这个阈值是在 Weizmann 那种
「固定机位 + 侧面 + 人贴画面边缘」的条件下标出来的，换到你的现场
（机位角度、像素密度不同）建议重新标一次——补标几十个片段跑一次
`--calibrate` 就行。

## 运行步骤

先做一次语法自检和模型形状自检（不训练，几秒钟）：

```
conda activate PLACE
cd scene_detect
python model.py
```

**第一步，抽骨架特征。** 对每个数据集跑一次，输出到独立目录：

```
python feature_extract.py ^
  --source "D:\SceneDetection\datasets\fall\urfall" ^
  --out    "D:\SceneDetection\features\urfall"
```

强烈建议第一次加上 `--save-vis`，先跑一两个视频，打开 `_vis` 目录下的视频
亲眼确认跟踪 ID 稳不稳、骨架有没有崩。这一步看几眼，比后面调一天参数有用。

**第二步，补标签。** 每个输出目录下的 `manifest.csv` 复制成 `labels.csv`，
加上三列 0/1 标签。三列全 0 就是「正常」，不需要单独建一类。

各数据集的标签建议：

| 数据集 | 目录 | running | falling | fighting |
|---|---|---|---|---|
| UR Fall | `urfall/fall-*` | 0 | **1** | 0 |
| UR Fall | `urfall/adl-*` | 0 | 0 | 0 |
| Unicomfacauca | `FALL-*` | 0 | **1** | 0 |
| Unicomfacauca | `ADL-*` `standing` | 0 | 0 | 0 |
| Bus Violence | `Violence/` | 0 | 0 | **1** |
| Bus Violence | `NoViolence/` | 0 | 0 | 0 |
| Weizmann | `run/` | **1** | 0 | 0 |
| Weizmann | `walk/` | 0 | 0 | 0 |
| Weizmann | 其余动作 | 0 | 0 | 0 |

**UR Fall 必须加 `--crop right`。** 它的 mp4 是「深度图 | 彩色图」左右拼接的
640x240，左半边是深度图，直接喂给 YOLO-Pose 基本检不出人：

```
python feature_extract.py --source "...\fall\urfall" --out "...\features\urfall" --crop right
```

**Unicomfacauca 整批是深度/红外图像**（已导帧确认），人是一个灰暗的剪影，
YOLO-Pose 在它上面不可用。这批 504 个视频暂时用不上，先留着：
如果之后想用，得换成专门的深度图姿态估计方法，或者只把它当作
「深度模态」的对照实验。**训练三类动作不要把它算进来。**

`walk` 一定要标进去当负样本——**奔跑和快步走在骨架特征上非常接近**，
没有走路样本，模型会把快走全判成奔跑。

把多个数据集的 `labels.csv` 合并成一个文件后训练：

```
python train.py --labels "D:\SceneDetection\features\labels.csv" ^
  --features-root "D:\SceneDetection\features" ^
  --labels-cols falling,fighting --epochs 60
```

`--labels-cols` 是奔跑改用规则之后加的：只训摔倒和打架两个头。
如果保留奔跑列一起训，它 509 倍的类别权重会产生很大的梯度，
把共享的时空特征一起带偏，摔倒和打架的指标也会跟着掉。

跑轻量基线做对比，看 ST-GCN 的图结构到底有没有带来收益：

```
python train.py --labels labels.csv --features-root "D:\SceneDetection\features" --model tcn
```

## 几个必须知道的点

**按视频划分，不按片段划分。** `split_by_group` 已经强制这么做了。
同一段视频切出来的相邻片段相似度极高，如果按片段随机划分，
验证集里的样本几乎都能在训练集里找到近邻，指标会虚高十几个点。

**每类各用各的阈值。** 训练产出的 `best.pt` 里存了 `thresholds` 字段，
是验证集上扫出来的每类最优阈值。接入实时推理时直接用它，
不要用固定的 0.5——数据不平衡时 0.5 会让召回率很难看。

**类别权重默认开启。** `BCEWithLogitsLoss` 的 `pos_weight` 按负正样本比自动算。
关掉它模型会躺平全判 0，准确率还很好看。

**打架这一类是当前方案的短板。** 本脚本处理的是单人骨架，
而打架本质是两个人之间的关系。现在这一版能抓到「挥拳、踢腿」这类
单人动作特征，但抓不到「两人肢体交缠」这种交互信息。
要真正解决得等里程碑 4，把相邻轨迹的交互特征（两人距离、相对速度、
关节间最小距离）接进模型。所以打架那一列现在准确率偏低是正常的，
不要为了刷高它就牺牲另外两类的阈值。

## 实时推理与界面（里程碑 3 和 1）

三个脚本，前两个是核心，第三个只是套了层界面：

| 文件 | 作用 |
|---|---|
| `pipeline.py` | 核心流水线：检测 → 跟踪 → 动作判定 → 投票报警 |
| `run_video.py` | 命令行跑单个视频，输出标注视频和事件记录 |
| `app_qt.py` | Qt 界面，加载视频实时检测报警 |

```
python run_video.py                     # 跑默认样例（UR Fall 的摔倒视频）
python run_video.py --source 你的视频.mp4 --show
python app_qt.py
```

实测在 320x240 的视频上跑到 36 fps，实时性没问题；1080p 会慢一些，
流水线会自动跳过节流、尽全力跑。

**报警逻辑是「投票 + 冷却」而不是逐帧触发**：最近 5 次判定里有 3 次为真
才报警，报警后同一轨迹同一个动作 8 秒内不重复报。不加这两层的话，
单次判定抖动会让画面疯狂闪红框，看几分钟人就不看了。

**打架默认不触发报警**，只在画面上标颜色。它现在精确率只有 0.5 左右，
真报警的话 70% 的正常片段会被报出来，很快你就对报警脱敏了。
界面上有开关，想看效果可以打开，但要知道这个前提。

### 「旁边没打架的人也被标成打架」——已收窄，但没有真正解决

**表面原因：标注粒度错了。** Bus Violence 的标签是**片段级**的（这段视频有暴力），
而我们的判定是**人级**的（这个人在打架）。我把片段标签盖到了片段里所有人的头上，
一段公交车上五个人只有两个在动手，另外三个旁观者也被标成「打架」，
于是模型学成了「这段视频里的人都算打架」。

**根因：骨架数据里没有能区分打架和正常的信号。** 这一点我实测过两轮：

| 候选线索 | 暴力片段 | 非暴力片段 |
|---|---|---|
| 本人运动量中位数 | 0.016 | 0.011 |
| 第二活跃者 / 最活跃者 | 0.57 | 0.57（90分位 0.90 / 0.91） |
| 两人最近关节距 ÷ 身高 | 0.30 | 0.27 |
| 有邻人的帧占比 | 0.93 | 0.93 |

四组分布几乎完全重合。用「第二活跃者比值」当单特征分类，F1 最高只有 0.57，
精确率卡在 0.46（而数据集本身的正样本比例是 47%，等于没学到东西）。

**目前的处理：加了一道「每帧最多标 2 人」的闸门**（`fight_max_tracks`）。
实测在 60 个暴力片段上，单帧同时被标的人数从「画面里有几个标几个」降到最多 2 个；
画面 3~4 人的片段，整段平均只标 2.58 个轨迹而不是全员。

这道闸门只是把伤害面收窄，**不代表剩下的两个人就是真的在打架**——
模型本身排不出谁在动手，闸门只是按分数取前几名。

**要真正解决，只能换模态。** 打架很可能得靠外观线索（肢体接触、姿态突变），
骨架版本已经在两轮实验里被否定。下一步值得做的是：拿同一批片段，
用 RGB 外观做一个极简基线（采样几帧过一个小分类器，甚至只用帧间差分能量），
看暴力与非暴力能否分开。这个测试几十分钟就能有结论，能一次性回答
「打架这条路到底通不通」。

## 双流方案：打架改用 RGB 外观

骨架模态在打架这件事上被四次实验否定之后，做了一次模态可行性验证，
结论很明确（`test_appearance.py`）：

| 方案 | AUROC |
|---|---|
| RGB 外观 全帧拼接（8帧） | **0.839** |
| RGB 外观 按时间块划分 | **0.810** |
| 纯运动量（帧间差分，1 维） | 0.749 |
| 骨架（各种几何特征，最好情况） | 约 0.55 |

而且按时间块划分后 AUROC 只掉 0.03，说明那不是相邻片段泄漏刷出来的。
于是打架改走外观支路，模型做成双流：

```
骨架支路  ST-GCN(48帧)              -> 256 维 ┐
                                              ├-> 拼接 -> 分类头 -> 判定
外观支路  ResNet18(8帧裁剪块) 卷积池化 -> 128 维 ┘
```

三个新脚本/改动：

``` 
python extract_appearance.py     # 给每个片段算 RGB 外观特征（约 2.5 分钟）
python train.py --model dual     # 训练双流模型
python app_qt.py                 # 界面已默认加载双流模型
```

`extract_appearance.py` 不重跑检测跟踪，直接按片段里已经存好的检测框裁剪，
所以只要两分半钟。每个片段存 8×512 的 float16 特征，总共约 30 MB。

**效果（验证集）：**

| 模型 | 打架 P | 打架 R | 打架 F1 | 摔倒 F1 | 宏 F1 |
|---|---|---|---|---|---|
| 纯骨架 60 轮 | 0.515 | 0.893 | 0.653 | 0.800 | 0.727 |
| 修正标注后 | 0.538 | 0.859 | 0.661 | 0.857 | 0.759 |
| 双流（外观坐标系有误） | 0.641 | 0.911 | 0.752 | 0.900 | 0.826 |
| **双流（修正后）** | **0.734** | 0.611 | 0.667 | **0.947** | **0.856** |

### 一个曾经让摔倒分支彻底失效的坑

第一版双流模型（`runs_dual`）的摔倒判定完全失灵——在测试视频上摔倒概率
恒为 0.000，一个报警都不出。原因是**两边的裁剪坐标系没对齐**：

UR Fall 的原始 mp4 是「深度图|彩色图」左右拼接的 640x240，抽骨架时裁掉了
左半边的深度图，所以片段里存的检测框是**裁完之后**的坐标系（x 大致在
0~320）。而 `extract_appearance.py` 一开始直接读了未裁剪的原图，按那些框
裁出来的是**左边深度图那一块**——摔倒这一类的外观训练输入全是垃圾。

修法是让 `extract_appearance.py` 用和抽骨架时完全一样的裁剪方式
（`resolve_crop`），然后删掉 `features/urfall/appearance.npz` 重抽、重训，
得到 `runs_dual2`。**流水线已默认用 `runs_dual2`。**

教训：离线抽特征和在线推理之间，任何一处坐标系、缩放、归一化的差异都会
让模型静默失效——它不会报错，只是输出恒为零。

修正后在测试视频上：摔倒段概率最高 1.000、21.2s 触发报警（真实倒地 20.53s，
滞后 0.67 秒）；公交场景的打架误标从 0.52/1.64 降到 0.43/0.99，
打架段 1.19——**之前正常片段被标得比打架段还多，现在顺序对了**。

**一个已知的代价：** 流水线现在要缓存最近若干帧的原图供外观支路裁剪，
1080p 下 48 帧约 300 MB。单路视频没问题，如果要同时跑很多路，
得改成缓存降采样后的副本并同步缩放检测框。

几何增强在外观支路启用时会被自动跳过（见 `dataset.py` 的说明）：
骨架翻转之后外观特征没法跟着翻，两条支路会对不上。

实测发现模型会在人还在正常走动时就报摔倒。根因查清了两层：

**第一层已经修掉：标注方式错了。** 一段摔倒视频会被切成好几个 48 帧片段，
原先把**全部**片段都标成 falling=1，包括最开头那段人还在直立走动的。
98 个摔倒正样本里有 24 个是这种情况。`relabel_falls.py` 按 UR Fall 官方的
逐帧标注（`urfall-cam0-falls.csv`，-1 未摔 / 0 正在倒地 / 1 已倒地）
重新标注，改成只有窗口里真的包含倒地过程才算正样本。

**第二层没解决：数据集层面的捷径。** 修完标注后在全部 30 段摔倒视频上测，
提前量中位数仍有 0.87 秒，11 段超过 1 秒，最差 4.9 秒。而且有直接证据：
fall-01 的头两个片段已经被改成负样本了，模型依然在那里输出 0.98 的摔倒概率。

原因是 UR Fall 的摔倒和日常活动是分两个场次录的，模型能靠与动作无关的
线索（走动方式、构图、光照）把「摔倒视频」和「日常活动视频」分开。
离线指标里摔倒 F1 看着有 0.8，其中一部分是这么刷出来的，不是真的识别动作。

试过在报警端加物理闸门（要求重心快速下坠或检测框由竖转横），实测不起作用：
朝镜头倒地时重心几乎不下移，而检测框高宽比在提前触发时就已经偏低。
强行打开反而会把真摔倒一起拦掉，变成漏报，所以默认关闭。

**结论：现在的摔倒检测不能当作"实时捕捉倒地瞬间"来信任。**
要真正解决，需要现场数据做微调（几十段就够），或者改成逐帧输出的时序检测
并用跨数据集验证来暴露这类捷径。

**`GMC failed, falling back to identity: ... lkpyramid.cpp ... SparsePyrLKOpticalFlow`**

这是 BoT-SORT 的全局运动补偿算不出光流，自动退化成「不做补偿」。
它被 try/except 包住，跟踪本身照常进行，不会中断，也不会报错退出。

产生原因是 `model.track()` 的 `persist` 参数用错了：`persist=True` 的含义是
「在多次逐帧调用之间保留跟踪器状态」，而我们是「一个视频调一次 track()」，
于是上一段视频的 GMC 状态被带进下一段视频。不同数据集分辨率不同
（UR Fall 裁完 320x240、Bus Violence 352x288、Weizmann 180x144），
拿上一段视频的灰度图去和这一段的算光流，金字塔尺寸对不上就触发了断言。

`feature_extract.py` 里已改为 `persist=False`。**除了这条警告，
用 True 还会让上一段视频的轨迹 ID 残留到新视频**，污染开头一秒左右的
ID 分配，所以修完值得重跑一遍特征提取。

如果你的场景本来就是固定机位，也可以直接把跟踪器换成
`--tracker bytetrack.yaml`：ByteTrack 不带 GMC，速度更快，
对这种场景几乎没有精度损失。
